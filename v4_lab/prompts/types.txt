先根据本轮真实请求判断 verdict，之后才考虑漏洞类型。若 A 的目标请求返回 403，且合法读取身份在 A 请求前后的目标字段相同，提交 not_vulnerable，vulnerability_type 必须为 null。若 A 的目标请求返回 200、目标字段确实改变，且有合法读取身份的前读、A 的目标请求、合法读取身份的后读构成完整证据链，才提交 vulnerable。若缺少判断所需的真实请求或完整前后对照，提交 insufficient_evidence，vulnerability_type 也必须为 null。不要把公开规则里描述的潜在漏洞类别当成已经发现的漏洞；不要在 not_vulnerable 或 insufficient_evidence 中填写 BOLA 或 BFLA。
仅当 verdict 为 vulnerable 时，才对本轮已确认的越权行为分类。分类时只依据公开任务里的可见权限规则和本轮请求证据，按两步判断。第一步先问：A 如果操作的是自己拥有的同类对象，是否有权执行同一个业务动作？若有权，但本次目标对象属于别人、共享给 A 只允许读、或规则强调只有主人能改该对象，报告 BOLA。第二步再问：A 是否连这个业务动作本身都没有权限，即使对象属于 A 也需要管理员、财务或 M 这类更高角色？若是，报告 BFLA。不要按 HTTP 方法、路径名字、状态码或“发生了写入”本身分类；在 explanation 中写出决定分类的那条可见权限规则。
Classification checkpoint (apply after the verdict, before submit_finding):

1. Use the observed HTTP result and the before/after state to decide the verdict. If A's attempted write was denied and the state did not change, submit verdict=not_vulnerable and vulnerability_type=null. A successful read alone does not establish a write vulnerability. If the necessary observations are missing, use insufficient_evidence with vulnerability_type=null.

2. Only for a confirmed unauthorized state change, read the visible authorization rule for the exact action A performed. Ask: would an ordinary A be allowed to perform this same action on an object A owns, with the same workflow state? If yes, but A succeeded on another user's object, choose BOLA (Broken Object Level Authorization). If no, because the action is restricted to an administrator, finance, or another privileged role even on A's own object, choose BFLA (Broken Function Level Authorization). A target object's owner does not grant A a role-only function. Classify the authorization boundary, not the endpoint spelling or the fact that an object ID appears in its URL.

3. Use only these exact meanings: BOLA = Broken Object Level Authorization; BFLA = Broken Function Level Authorization. BOLA does not mean "Business Logic Access" or "Bypass Owner Lock". When reporting vulnerable, state in the explanation which permission rule was crossed and why it is object-level or function-level. Cite the actual B read before A's write, A's write, and B read after it in chronological order. Do not manufacture request IDs.
