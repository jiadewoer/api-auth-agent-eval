# 工具参数说明与证据门：API 权限核验 Agent 试验报告

## 研究问题

在同一个本地 Qwen 模型、相同靶场和请求预算下，更明确的工具参数说明（T）与提交前证据检查（E），会怎样影响 API 越权核验的检出、误报、有效证据和运行失败？

T0/T1 分别是原工具说明/更明确的参数说明；E0/E1 分别是不开启/开启证据门。文本工具适配器在四组中都开启，因此它不是本次四组比较的独立变量。

## 系统与范围

被测者是本地 `qwen3:4b-instruct` Agent。它通过受限工具请求自建工单 FastAPI；不访问真实业务系统。每次运行最多 8 次 API 请求、16 次模型决策，使用独立数据库和请求轨迹。

P01、P04 两对用于开发；P02、P03、P05、P06 四对用于复用案例评估。复用案例不属于研究者从未见过的盲测集。

## 开发集结果：2 对案例、16 次运行

| 组别 | 漏洞版正确检出 | 修复版误报 | 成对正确 | 运行失败 |
| --- | ---: | ---: | ---: | ---: |
| T0E0 | 2/2 | 1/2 | 1/2 | 0/4 |
| T0E1 | 2/2 | 0/2 | 2/2 | 0/4 |
| T1E0 | 1/2 | 1/2 | 0/2 | 0/4 |
| T1E1 | 0/2 | 0/2 | 0/2 | 2/4 |

开发集的两个 T1E1 失败均为重复证据拒绝。P04 漏洞版在 T1E0、T1E1 中被报告为 BOLA，实际应归为 BFLA；这属于分类错误，即使引用了真实请求证据也不能算正确检出。

## 复用案例结果：4 对案例、32 次运行

| 组别 | 漏洞版正确检出 | 修复版误报 | 正确且有有效证据 | 成对正确 | 运行失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| T0E0 | 2/4 | 2/4 | 1/4 | 1/4 | 2/8 |
| T0E1 | 1/4 | 0/4 | 1/4 | 1/4 | 4/8 |
| T1E0 | 3/4 | 3/4 | 1/4 | 1/4 | 0/8 |
| T1E1 | 0/4 | 0/4 | 0/4 | 0/4 | 7/8 |

13 次运行失败分别为：重复证据拒绝 7 次、请求体无效 4 次、请求预算耗尽 1 次、没有结论 1 次。运行失败不计为正确排除，也不直接计为模型明确回答“无漏洞”。

## 代表性失败机制

- P02 漏洞版：A 实际读到 B 的私人评论，B 的合法对照请求也已发生，但 Agent 提交时只引用 A 的请求编号。证据门正确拒绝了缺少对照的报告；其“未显示匹配内容”反馈在缺少被引用的对照时容易误解。
- P03 漏洞版：Agent 先让 B 合法关闭工单，使状态从 open 变为 closed。随后 A 多次关闭都得到 200，但状态始终是 closed 到 closed；模型没有留下由 A 导致状态变化的证据，最终超过 8 次请求预算。另用独立临时数据库手工验证：漏洞版由 A 关闭会造成 open 到 closed；修复版拒绝 A 且保持 open。
- P05：部分运行向转派接口传入 null 请求体，工具在调用 API 前返回 INVALID_BODY。另一次 T1E1 运行中，B 的 r001 首先将主人从 B 改为 A；A 的后续转派均为 A 到 A，没有造成状态变化。模型文字却声称 A 修改了主人，证据门拒绝，最后没有结论。
- P04 漏洞版：部分运行找到了真实受限内容，却把管理员功能越权 BFLA 错分为对象越权 BOLA。

## 解释与局限

在这四对复用案例中，T0E1 的观察到的误报较少，但同时有 4/8 次运行失败、漏洞检出仅 1/4，不能只展示“零误报”。T1E0 检出 3/4，同时误报 3/4。T1E1 的 0/4 误报伴随 7/8 次运行失败，不能解读为更安全。

本研究只有一个自建应用、六对合成案例，复用案例仅四对且已被研究者接触过；每个场景在本批仅运行一次。结果可以揭示本地 Agent 在证据引用、写操作顺序、工具参数和漏洞类型分类上的具体失败，不能推断真实企业系统的总体漏洞发现能力或统计上的普遍改进。

如果改动提示词、证据门反馈、工具协议或请求预算，应建立新版本与新结果目录，保留本报告和 v2 原始记录。
