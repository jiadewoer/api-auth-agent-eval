# 迈向论文的研究协议草案（未来实验，尚未预注册）

## 1. 审稿人首先会问什么

**研究问题**：交互式 Web/API 权限核验中，在相同的请求与决策预算下，改进工具参数说明 T 和基于真实可见请求的提交前证据检查 E，是否能提高跨应用的可归因成功率？收益会不会换来更多漏报、拒答、预算耗尽或时间成本？

**潜在贡献**：让模型明确连接“身份 → 目标资源 → 合法对照 → 待验证请求 → 受保护数据或写入后的状态”，用成对修复版排除只看 `200` 或只见合法共享的错觉；针对交互式 API、跨身份请求和有副作用的写操作设计可复核的证据链及干预。不能主张“首次把结论和证据分开”，已有研究在 PR 安全审查中采用类似思路。

**定位**：这是“已知候选接口的权限核验”任务；不能写成全站自动漏洞发现，也不能用测试友好靶场的表现代表真实企业应用。

## 2. 和已有研究的关系

- [CVE-Bench, ICML 2025](https://proceedings.mlr.press/v267/zhu25i.html) 在真实 Web 漏洞环境评测 Agent，证明仅用一个自建应用支撑广泛结论不够。
- [Agentic Benchmark Checklist, NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/hash/f316275b44ee2de533102913828a8107-Abstract-Datasets_and_Benchmarks_Track.html) 强调任务与结果的有效性，要报告 oracle 错判与不合理任务的风险。
- [From Verdict to Diagnosis, 2026 预印本](https://arxiv.org/abs/2608.25730) 已研究结论与可归因证据的差别，任务是 PR 审查。你要通过**交互式跨身份动作、写入状态与跨应用转移**建立区别，不能把“证据评分”本身当新颖性。

正式投稿前重新检索最新相关论文，明确负面结果或无效结果的价值。论文接收取决于创新性和严格的外部评审，下面仅是可执行的改进路线。

## 3. 数据集从一个应用变成多个应用

**先做迁移检查**：增加费用报销系统和多租户文档系统，各 4 对开发案例，验证原 Agent 的路由白名单、身份注入、状态快照、证据检查能否换环境使用。现在的 `/tickets/201` 硬编码需要被“任务合同”代替：合同说明可用方法和相对路径、合法/待测身份、公开业务权限、对照观察接口与可见字段；内部真值和受保护标记保留在独立评分器。不能把合同的预期结果直接返回给 Agent。

**正式研究目标，不是魔法录用门槛**：至少 5 个彼此独立的应用实现，合计约 50 对经人工复核的 vuln/fixed 案例，每个应用覆盖读与写、对象授权与功能授权、正常共享或委托、无效对象、重复写入等反例。可包括经授权隔离的开源靶场或公开修复提交，但必须记录许可、来源、提交哈希、漏洞范围与复现步骤。不同数据行不能仅换 ID 或字符串就算新案例。新的正式应用应在方法冻结后才跑模型；已查看实现的研究者可以如实说**模型未用于调参的应用保留集**，不能说研究者也完全不知真值。

每对登记：`app_id`、`pair_id`、来源/版本、场景类型、初始数据哈希、公开任务哈希、唯一授权变动的代码差异、合法对照、候选未授权请求、读取内容或前后状态 oracle、正负结果、双人复核/分歧记录。批量生成的样例按同一模板簇追踪，划分数据时整簇进入同一集合。

### 人工与自动质量门

1. 脚本从零重置两版；比较种子数据与公开任务字节完全一致，只允许一个预定授权检查改变。
2. 用固定脚本执行合法身份与未经授权身份的相同请求；读类校验敏感字段来自未授权响应，写类校验请求前后真实状态与是否有其他写入干扰。`200` 但没有变化不能证明写越权。
3. 加入**困难负例**：合法共享主体不含私人评论、成功状态但无状态变化、管理员可访问并不推出普通用户可转派、拒绝响应只出现公共字段、已关闭再关闭。
4. 第二人只看任务说明与授权规则，独立给出预期；有分歧先改题并标记版本。记录可疑标记是否通过 `docs`、错误信息、顺序、任务编号泄漏。
5. 为多应用提供统一受限工具接口，服务器地址和令牌由程序注入；模型只可传身份、方法、允许路径和受限请求体。环境参数与 oracle 永不进入提示或工具反馈。

## 4. 未来 2×2 方法对照和必要消融

`T0E0`：原工具说明、无证据门；`T1E0`：清晰的工具参数说明；`T0E1`：原说明加证据门；`T1E1`：两者都有。四组**同一模型、同一公开任务、同样请求与决策上限、同一总时间限制**；每次新数据库、新对话与新日志；案例顺序交替或在冻结随机种子下分块随机。模型 digest、提示词、工具 schema、版本哈希都保留。

现有 E1 会提供反馈与重试，可能改变信息量。增加一组“只校验提交格式、同样允许重试”的安慰剂门，或在论文中明确 E1 的差异包括额外反馈；比较 `T0E0`/`T0E1` 不能简单称为“只有一句提示不同”。工具说明改良也会带来 token 差异，记录工具 schema token 量。再做去掉合法对照要求、去掉写前后观察的消融，以定位贡献。冻结后不因保留集表现不好再改门槛。

**模型与基线**：先用 Qwen3 4B 打通跨应用；正式对照至少覆盖两个不同模型家族或能力等级，并加固定流程脚本作为“已知接口且规则手写”的参照。固定脚本不是公平的通用 Agent 对手，分开讨论先验信息。若能请一名熟悉 Web 授权的人在一小部分案例盲审，量化靶场可理解性和 oracle 分歧。

## 5. 在看未来结果之前冻结统计约定

**主终点：可归因的成对成功**。同一应用同一案例对同一重复下，漏洞版分类与类型正确、有引用到本人真实请求的有效证据；修复版正确排除；任意一个技术失败都计这次成对尝试未成功。它衡量的是完整核验，不是只会说“有漏洞”。

**次终点**：漏洞检出、修复版误报、合法共享误报、错类型、弃答、技术失败细类、有效证据/所有漏洞报告、API 请求数、模型决策数、耗时、token 与显存/CPU 退化。保留意向运行分母，不仅看成功提交的样本；无结论另列。报告每个应用结果和应用类型异质性。

**分析单位**：应用为迁移单位；同一应用内的案例对是相关任务；同一对的两版及重复运行是成组观察。先求每对在重复中的差异、每应用内平均，再等权汇总应用差异。仅应用数达到五时使用按应用和案例对层级重采样的**探索性** 95% 区间；应用数更少不报告跨应用区间。主要效应、比较方向、缺失/技术失败处理与多指标优先级在新保留集首次运行前写入带哈希的清单；如需正式推断，再根据开发集估计效应和方差做功效与样本量规划。不要把重复 2 次声称得到 2 个独立新案例。

**事后标签**：旧 A/B 32 次与复用六对的 T×E 结果都是先导或机制诊断，不可追溯地改称事前预注册。新应用的设计文件和判分代码先冻结、另建 `results/prospective-YYYYMMDD/` 后才执行正式评估。系统故障按预定全批处理，不挑有利案例补跑。

## 6. 4060 笔记本的现实顺序

1. 这周：运行本目录审计与旧数据分析；补读上述三篇原始论文，写一页你的**不同点与重叠点**。
2. 后续 2–4 周：把路由、身份、只读观察与写状态 oracle 抽成每应用适配器；第二个应用先做 2 对，跑固定脚本与四组的开发诊断，确保没有路径硬编码。每个新增案例先手工独立复现。
3. 后续 1–2 个月：逐个增加真实差异的应用与案例，做第二人审核；至少 5 个独立应用是目前分析器输出跨应用探索性区间的门槛，但仍非顶会保证。
4. 冻结后先用小批量测每次的实际时间和显存，再估算总量。若 50 对 × 2 版本 × 4 组 × 2 次重复，是**每个模型 800 次运行**；两个模型是 1600 次，单台笔记本可能要多天到数周。先安排夜间串行和断点续跑，不要牺牲案例质量凑数字；算力不足时缩小方法对照并如实降低主张。
5. 报告完整资源限制、失败日志、设计与源码；找同行读过案例与评测脚本，再决定冲击安全或机器学习评测会议的合适赛道。没有外部应用和新保留结果之前，定位仍是优秀工程作品与研究先导实验。

## 7. 论文写法的最低证据表

| 论文主张 | 必需证据 | 当前是否具备 |
| --- | --- | --- |
| 可复现的单应用授权评测 | 两版真值、自动测试、轨迹与 32 次结果 | 有，作为先导 |
| T、E 对结果有因果效应 | 冻结 2×2 对照、真实模型运行、代价与消融 | 实现四组；尚无真实运行 |
| 能跨应用迁移 | 独立应用、应用级保留、按应用报告结果 | 尚无 |
| 证据门优于简单格式检查 | 安慰剂门、反例、有效证据验证 | 部分单应用反例；正式消融未做 |
| 可提出广泛的网安 Agent 结论 | 异质应用、模型、专家复核与透明区间 | 尚无 |

先把“有效证据是什么”和“不同应用也成立吗”证实，再决定论文标题和投稿场合。
