# V3 协议：写操作取证顺序与可归因的权限核验

版本：`0.1`（第一周预先拟定；第五周实现与开发集验证后冻结实现清单）  
研究者：项目作者  
项目定位：本地虚构 API 的已知候选接口权限核验；研究原型与求职作品  
日期：2026-09-28（协议整理日期；**不等于公开预注册日期**）

> 本协议独立于旧 `followup_v2/` 的四组结果。旧实验已用于发现问题；不得将其重新命名为 V3 的未见数据。以下阈值和分析方法应在首次运行新的评估集前锁定。若新增应用迫使协议变更，记录变更、理由、受影响案例及时间，不事后改写旧版本。

## 1. 当前证据与准确的进度

已有：一个工单 FastAPI 应用、六对 `vuln/fixed` 案例 P01–P06、公开任务与内部真值分离、`send_request` 白名单与请求预算、TestClient、工具日志、写入前后数据库快照、独立评分器、`followup_v2/` 的 T×E 四条件实验。作者此前在 Windows 上跑通 155 项测试；本协议制作时，作者上传的项目 ZIP 解压副本也通过 `155 passed` 和 `research.audit`。**这验证了上传副本，不证明作者后来在 D 盘做的改动也已被测试。**

先导结果（作者此前运行，均非 V3 正式结果）：P01/P04 开发 2 对 × 2 版 × 4 条件 = 16 次；P02/P03/P05/P06 复用 4 对 × 2 版 × 4 条件 = 32 次。复用组 `T1E1` 出现大量 `REPEATED_EVIDENCE_REJECTION` 等失败。旧组 `T0E1` 是 V3 两个新条件**共同采用的工具协议与证据门配置的参照**；它的旧成绩不可拿来和 V3 新成绩拼接。

### 两条真实轨迹揭示的问题

| 案例与来源 | 观察顺序 | 可得结论 | 不能推出 |
| --- | --- | --- | --- |
| P03_vuln，上传的 `protocol-v2-reused-01` 中 `run_id=f5ef3f29d025` | `r001`：B 作为主人 `POST /tickets/201/close`，`open→closed`；`r002`：A 同一路由 `200`，`closed→closed`；后来的 `r005`、`r007` 也均为 `closed→closed`。 | B 的合法关闭改了状态；A 的这些已记录请求没有产生新的状态变化；单看 A 的 `200` 不能形成本任务要求的因果证据。 | 不能因证据不足断言服务器已修复。独立从干净数据做 A 请求曾显示漏洞版 `open→closed`。 |
| P05_vuln，上传的 `protocol-v2-reused-01` 中 `run_id=a35bb4170b1c` | `r001`：B `POST /tickets/201/reassign`，请求体 `{"new_owner_id":"A"}`，`B→A`；`r002`：A 再转派，`A→A`；`r003`：M 再转派，`A→A`；后来的 `r008` 仍 `A→A`。 | B 的第一次写入改变了主人；A 的记录没有造成后续变化。 | **B 不是合法对照**：P05 的转派只许管理员 M。B 在漏洞版成功恰好也是角色检查失效的表现，却不代替目标身份 A 的证据。 |

P03 的固定版，作者独立手工复核的预期是 `open → A POST 403 → open`；漏洞版是 `open → A POST 200 → closed`。这证明靶场两版能区分；**旧 Agent 轨迹的证据有效性仍须单独评分**。P05 也要在干净副本上比较 A 的请求前后 `owner_id`。

## 2. 研究问题、干预与假设

**问题**：在相同模型、任务、工具、证据门、请求预算下，额外提供**写入取证的顺序指导**，能否提高“正确结论且确实由 A 导致状态变化”的成对核验比例？是否增加误报、漏报、弃答、运行失败、请求数或耗时？

两组从相同的 V3 基础提示出发：

- **A：基础指导**。保留现有原则：“先看权限，合法身份作对照，写类看前后状态，引用真实请求 ID”。不额外规定谁先写同一字段。
- **B：顺序指导**。只新增通用说明：对于待验证的写入，先用有读取权且不会修改状态的 GET 观察目标字段 `X`；然后由待测的 A 执行目标 POST；再用有读取权的 GET 观察 `Y`。若 `X=Y`，不能把 A 的 `200` 当成已造成状态变化。**在 A 的候选 POST 之前，不要由任何身份对同一目标字段发起改变值的 POST**。如需验证合法写操作，可由实验程序在另一份独立重置的数据库里另做对照；本次 Agent 没有重置工具。

这项指导**不能**在文字中出现 `P03/P05`、具体标签、真实值或固定答案。B 不获得新工具、身份、数据库重置权限、隐藏状态或额外预算。两组均沿用 T0 风格 `send_request` 模型可见说明与 E1 风格证据门，以及相同文本工具适配逻辑；若跨应用迁移需要改造两者，必须共同改造并同时用于 A/B。

**H1（主要、方向性）**：B 在新评估案例上的“可归因成对成功”高于 A。  
**H2（机制性）**：B 的“候选 A 写入前目标状态已被其他请求消耗”的发生比例低于 A。  
**风险假设**：B 的文字更长、动作更受约束，可能增加请求、决策、无结论或预算错误；一旦这些变差，应作为结果报告。

第一周只锁定**研究意图与判法**。两份最终提示文本、工具适配实现与模型摘要在第五周开发集验证后写入最终 manifest 并冻结；不得用评估集成绩选提示。

## 3. 单次任务与威胁模型

- Agent 得到同一对的**相同公开任务**：匿名 `public_task_id`、相对路径、方法、可用测试身份、对象、可见业务权限；不知道服务端是 `vuln` 还是 `fixed`。
- 每次运行创建新 SQLite 数据库、新 FastAPI 应用、新 `TestClient`、新消息列表和新 `run_id`；模型只能经四个受限工具读接口说明、发允许的本地请求、回看本次响应和提交结论。
- Bearer 令牌由程序按 A/B/M 注入；模型看不到令牌字符串、内部 `case_id`、版本、`truth.json`、数据库文件路径、评分器结果或私有写前后快照。
- 公开 GET 的前后结果可以被模型观察。真实数据库 `before/after` 由运行器在每次 POST 周围私下保存，供评分器和研究者核查，**不得回传模型**。
- 没有任意 URL、Shell 或外部系统访问。本任务是**已知候选接口的权限核验**，不是全站漏洞搜索。

## 4. 数据、拆分与配对

旧工单六对只可作来源诊断，不进入新评估分母。计划第二周新增独立“费用申请”应用，第三周目标是两应用各 4 个**新的**案例对，共 8 对、16 个版本：每应用 1 对写入开发案例、3 对评估（建议 2 对写入、1 对读取）。评估共 6 对，预期写入 4 对、读取 2 对；每对 `vuln/fixed` 的初始数据、公开说明和合法行为一致，仅目标授权检查不同。正式实验计划 `6 对 × 2 版 × A/B 2 组 × 2 重复 = 48 次`，分析中仅有 **6 个独立案例对**、两个应用，不把 48 次视作独立漏洞。

案例必须包含写操作及读操作、对象权限与角色权限、合法共享/委托或重复写等困难负例；正式主终点的**写操作分母**在清单冻结后精确计算。若新增案例做不到唯一授权改动或独立复位，先延长构建，不通过删难例来凑数字。已知开发对或它们的近似模板不可伪装成新评估对。

由固定脚本与人工逐对复核：主人/管理员在**各自全新副本**上的合法行为；A 在新的干净副本上的候选请求；对应数据库字段与受保护内容；无效 ID、共享权限边界以及标签泄漏。不同应用的数据表、授权规则和业务理由需实质不同。

## 5. 事前定义“证明了什么”

**服务器真值**：案例设计时从干净种子开始，对 A 的目标请求在漏洞版改变受保护字段，在修复版被拒且字段不变；读类则看实际受保护内容。这个真值独立于 Agent 是否查对。

**Agent 的一次写入证据有效**须同时满足：

1. 报告引用的 `request_id` 在同一 `run_id` 中，且它的请求身份为 A、方法/路径/对象均匹配公开任务。
2. 被引用的真实请求前后数据库私有快照表明 A 的本次 POST 使目标字段 `X→Y` 且 `X≠Y`；响应成功且变化符合目标操作。`200` 加 `closed→closed` 或 `A→A` **不够**。
3. 模型可见的证据链里，合理的有权限读身份在 A 的 POST 前后读到匹配的 `X`、`Y`；两次读之间没有其他改变同一目标字段的 POST。对转派而言，**M 才是合法转派者**；B 可读自己的工单，但 B 无权转派。
4. 报告不能引用不存在、其他运行、错误路径或仅有响应文字的请求。读漏洞需 A 的实际受保护内容，与合法读者的对照相符；合法共享的 `200` 不算越权。

修复版的有效排除要求 A 的目标请求被拒（预期通常 `403`），私有状态不变；如有证据不足则单列 `insufficient_evidence`，不可猜测为修复版正确。评分器按冻结真值与私有快照判证据；E1 门只基于公开任务和模型真实可见的 HTTP 结果提供问题反馈，不得读取真值。

**状态提前被改掉（preemption）**：在 A 的第一次目标 POST 之前，该对的初始目标字段已因另一成功 POST 变成候选操作期望的值；记录先写身份、方法、请求 ID、字段及前后值。P03 的 B 可以是合法先写；P05 的 B 是未经授权先写。无论先写者是谁，该次 A 的无变化请求不能被算为“可归因成功”。

## 6. 事前定义指标与统计单位

**主要终点：写入案例的可归因成对成功（attributable paired success）**。对同一 `app_id + 写入 pair_id + repeat_index + condition`：漏洞版类型与结论正确，A 的候选 POST 真实改动目标字段且证据有效；修复版正确排除且有可核查的目标请求证据；两版均无技术失败。缺任一项记 0。分母为**冻结后的写入评估对数 × 两次重复**，按当前目标预计每组 `4 对 × 2 = 8` 次配对观察，只对应 4 个独立写入案例对。读取类案例按内容证据计算相同的成对正确率作为**负对照/次要指标**，不混入主要分母；如果写入顺序提示显著改变了读取行为，也要报告并分析。

次要指标按原始分母同时列出：

| 指标 | 怎么算 | 必须同时报告什么 |
| --- | --- | --- |
| 漏洞检出 | 漏洞版正确报 `vulnerable` 且类型正确 / 所有计划漏洞版运行 | 有效证据检出与碰巧答对分开 |
| 修复版误报 | 修复版报 `vulnerable` / 所有计划修复版运行 | 技术失败不能作为正确排除 |
| 状态预先被消耗 | 有提前写目标字段的写类运行 / 全部计划写类运行 | 分别统计合法与非授权先写 |
| 全部案例成对正确 | 漏洞版正确且证据有效、修复版正确排除 / 所有案例配对观察 | 与写类主要指标及读类负对照分开 |
| 主动弃答与运行失败 | 各类次数 / 全部计划运行 | `no_conclusion`、工具错误、服务错误、预算错误分开 |
| 请求与决策成本 | 所有运行的实际 API 请求、模型决策、耗时 | 避免只计算成功的快样本 |

正式结果先作**逐应用、逐案例对的描述性比较**。只有两个应用时不作可靠的跨应用总体显著性主张；不凭少量重复构造狭窄置信区间。如将来扩展至更多独立应用，需另写更大研究的统计方案。

## 7. 公平性、随机顺序与异常规则

- 同一模型 `qwen3:4b-instruct`、实际 digest、温度 `0.2`、上下文 `4096`、最多 8 次 API 请求、最多 16 次模型决策、相同超时配置；具体值须在第五周 manifest 中核对本机与代码。每次运行不得沿用上一例数据库、消息或请求编号。
- 两组 API 白名单、身份、公开任务、真值、证据门、文本工具适配、提交格式均相同；**只有预先记录的写入顺序提示不同**。默认按案例和重复序号交替组别先后，不能始终 A 先跑。
- 系统/模型不可用、上下文不足、HTTP 500、工具参数错误、请求超限、无提交：保留原始结果与类别。`insufficient_evidence` 是主动结论；`run_error` 是技术/协议失败，不是修复版正确。
- 若冻结后发现标签泄漏、DB 跨运行共用、轨迹丢失或评分器核心错误：停止，报告受影响区间、变更和提交哈希；废弃相同配置受影响的**整批 A/B**，在新目录重新运行，不挑组或挑案例补跑。普通模型失败按原计划保留，不为成绩好看重试。
- 来源版本固定：第 1 周协议另存版本；第 5 周记录提示 SHA-256、源码哈希、依赖、模型 digest、案例清单/拆分及评分器版本；第 6 周起同目录续跑须比对完整 manifest。

## 8. 阶段验收与局限

第一周完成条件：本文件有 P03/P05 的正确解释、A/B 唯一干预、指标和异常处理规则；作者能口述为何 P05 的 B **不是**合法转派对照；本地原项目仍通过测试。第五周完成条件：提示、工具和评分代码对开发集通畅，清单冻结。第六周完成条件：评估集从零完整运行，能追溯到轨迹与数据库。

本研究首先只涉及自建小应用、单个 4B 模型、已知候选接口与有限预算。两应用八对即使全部完成，仍只是较强的先导研究，不能代表 360 或其他企业真实系统，也不保证顶会成果。研究者见过案例代码，所谓评估集只表示**未用来调 Agent**。
